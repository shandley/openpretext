
with (L29-L30):

```cpp

```

So a default 1.0.7 export begins with exactly three lines:

```
##agp-version<TAB>2.1
# DESCRIPTION: Generated by PretextViewAI Version 1.0.7
# HiC MAP RESOLUTION: <float, %f so 6 decimals> bp/texel
```

Points that matter for compatibility:

- The separator after `##agp-version` is a TAB, not a space.
- With "Format Singletons" ticked the version value is the literal string `<NA>` and a fourth line `# WARNING: Non-standard AGP, singletons may be reverse-complemented` is added.
- The resolution line is `Total_Genome_Length / Number_of_Pixels_1D`. Downstream tools read it. Sanger's `agp-tpf-utils` parses it with `re.match(r"HiC MAP RESOLUTION: ([\d\.]+) bp/texel", txt)` (https://github.com/sanger-tol/agp-tpf-utils/blob/74af3fbc3a3a30a0c3434b3282f1dc44319493f5/src/tola/assembly/assembly.py#L72), and PretextView's own "Load AGP" needs it (`src/parse_agp.h`, regex `^# HiC MAP RESOLUTION:\s*(\d+.\d*)\s+bp/texel\s*$`).
- Before 1.0.0 the program name in the DESCRIPTION line was `PretextView Version x.y.z`; from 1.0.0 it is `PretextViewAI Version x.y.z` (see section 7).

## 2. Sequence (W) rows, column by column

The writer loops over `Contigs->contigs_arr`, which is the list of map fragments in current map (display) order, rebuilt from per-pixel state by `UpdateContigsFromMapState()` (L2261).

Painted fragment, L13235:

```cpp
stbsp_snprintf(buffer, sizeof(buffer), "Scaffold_%u\t%" PRIu64 "\t%" PRIu64 "\t%u\tW\t%s\t%" PRIu64 "\t%" PRIu64 "\t%s\tPainted", scaffId, scaffCoord_Start, scaffCoord_End, ++scaffPart, contName, contRealStartCoord, contRealEndCoord, invert ? "-" : "+");
```

Unpainted fragment, L13255:

```cpp
stbsp_snprintf(buffer, sizeof(buffer), "Scaffold_%u\t1\t%" PRIu64 "\t1\tW\t%s\t%" PRIu64 "\t%" PRIu64 "\t%s", (preserveOrder ? ++scaffId_unPainted : ++scaffId), contRealSize, contName, contRealStartCoord, contRealEndCoord, invert ? "-" : "+");
```

| Col | Painted fragment | Unpainted fragment |
|---|---|---|
| 1 object | `Scaffold_<scaffId>` | `Scaffold_<next number>`, one object per fragment |
| 2 object_beg | running `scaffCoord_Start`, starts at 1 for each scaffold | literal `1` |
| 3 object_end | `scaffCoord_Start + contRealSize - 1` | `contRealSize` |
| 4 part_number | `++scaffPart`, shared counter with gap rows, so W rows are 1, 3, 5, ... | literal `1` |
| 5 type | `W` | `W` |
| 6 component_id | name of the original contig from the `.pretext` header | same |
| 7 component_beg | `contRealStartCoord` | same |
| 8 component_end | `contRealEndCoord` | same |
| 9 orientation | `+` or `-` (see below) | `+` or `-` (always `+` unless Format Singletons) |
| 10+ | literal `Painted`, then tag names | tag names only (no `Painted`) |

### Component id

L13212:

```cpp
char *contName = (char *)((Original_Contigs + cont->originalContigId)->name);
```

`cont->originalContigId` is the base id of the original contig (set in `UpdateContigsFromMapState` as `last_cont->originalContigId = lastId_original_contig_base;`). There is no fragment suffix. A cut contig appears as several W rows carrying the same component id with different component_beg/component_end ranges.

### Coordinate arithmetic (the important part)

L13196-L13210:

```cpp
u08 invert = IsContigInverted( index );
u32 startCoord = cont->startCoord - (invert ? (cont->length - 1) : 0);
...
u64 contRealStartCoord = (u64)((f64)startCoord / (f64)Number_of_Pixels_1D * (f64)Total_Genome_Length) + 1;
u64 contRealEndCoord = (u64)((f64)(startCoord + cont->length) / (f64)Number_of_Pixels_1D * (f64)Total_Genome_Length);
u64 contRealSize = contRealEndCoord - contRealStartCoord + 1;
```

- `cont->startCoord` and `cont->length` are in map pixels. `startCoord` is the fragment's position within its original contig (`contigRelCoords`, a per-pixel counter starting at 0 at the first pixel of each original contig; struct comment in `src/genomeData.h`: `u32 startCoord; // local coordinate on the original contig`). For an inverted fragment the stored start is the high end, so the code subtracts `length - 1` to get the low pixel.
- So: `component_beg = floor(p0 * L / N) + 1` and `component_end = floor((p0 + len) * L / N)`, where `p0` is the fragment's first pixel within its original contig, `len` its pixel length, `L = Total_Genome_Length`, `N = Number_of_Pixels_1D`. The cast to `u64` truncates.
- Coordinates are 1-based inclusive. A fragment starting at pixel 0 gets component_beg 1. Adjacent fragments of one contig tile exactly: the end of one is `floor(k*L/N)` and the start of the next is `floor(k*L/N) + 1`.
- Yes, bp are pixel index times bp-per-pixel. No real contig lengths are used. The last fragment of a contig ends at a pixel boundary, not at the contig's true length. In the pre-AGPCorrect example below, one-pixel contigs all come out as `1..36397` at 36397.49 bp/texel.
- object_end is computed from `contRealSize`, so object coordinates carry the same pixel rounding.

Why the true lengths are unavailable: on load the per-contig fractional lengths are converted to pixel spans and then thrown away. Comment at L7466-L7470:

```cpp
// If we kept `contigFracs` instead of deleting it, we could retrieve
// all the contigs within each pixel.  These are otherwise lost in
// the AGP output when there are multiple, short contigs within a
// pixel.
delete[] contigFracs;
```

Contigs that do not own a pixel are never in `Contigs->contigs_arr` and therefore never appear in the AGP.

### Orientation

L13206:

```cpp
invert = (!formatSingletons && (!cont->scaffId || (index && (index < (Contigs->numberOfContigs - 1)) && (cont->scaffId != ((cont + 1)->scaffId)) && (cont->scaffId != ((cont - 1)->scaffId))) || (!index && (cont->scaffId != ((cont + 1)->scaffId))) || ((index == (Contigs->numberOfContigs - 1)) && (cont->scaffId != ((cont - 1)->scaffId))))) ? 0 : invert;
```

With Format Singletons off (the default), orientation is forced to `+` when the fragment is unpainted, or is the only fragment in its painted scaffold. Otherwise `-` is written when the fragment is inverted on the map. The coordinates are computed before this override, so they are still correct for the fragment; only the sign is dropped. With Format Singletons on, the map orientation is always written (and the header becomes non-standard, section 1).

## 3. Gap rows

L13225-L13232:

```cpp
if (scaffPart)
{
    scaffCoord_End = scaffCoord_Start + 99;
    stbsp_snprintf(buffer, sizeof(buffer), "Scaffold_%u\t%" PRIu64 "\t%" PRIu64 "\t%u\tU\t100\tscaffold\tyes\tproximity_ligation\n", scaffId, scaffCoord_Start, scaffCoord_End, ++scaffPart);
    fwrite(buffer, 1, strlen(buffer), file);

    scaffCoord_Start = scaffCoord_End + 1;
}
```

- Component type `U`, gap length `100`, gap type `scaffold`, linkage `yes`, evidence `proximity_ligation`. Nine columns, no extras.
- One gap row is written before every W row of a painted scaffold except the first. That is every adjacent pair of fragments in a painted scaffold, with no exception for two fragments that come from the same original contig.
- Gap rows consume a part number and 100 bp of object coordinates.
- Unpainted fragments are single-row objects and never have gaps.
- Original gaps inside input scaffolds are not represented. Components are the sequences in the `.pretext` file, whatever they were.

## 4. Extra columns: `Painted` and meta-data tags

Painted W rows always get a 10th column with the literal `Painted` (it is inside the format string at L13235). Then, for both painted and unpainted rows, each set tag is appended as one more tab-separated column (L13237-L13250, and again L13257-L13270):

```cpp
if (*cont->metaDataFlags)
{
    ForLoop2(ArrayCount(Meta_Data->tags))
    {
        if (*cont->metaDataFlags & (1ULL << index2) &&  // NOTE: please make sure the 1ULL, or after index2 >= 32 there will be unexpected behaviour
            Grey_Out_Settings->paint_tags.count(std::string((char*)Meta_Data->tags[index2])) == 0  // make sure this is not tag used for vertical horizontal or cross painting
        ) 
        {
            stbsp_snprintf(buffer, sizeof(buffer), "\t%s", (char *)Meta_Data->tags[index2]);
            fwrite(buffer, 1, strlen(buffer), file);
        }
    }
}
fwrite("\n", 1, 1, file);
```

- Tags are written in tag-slot order (bit 0 first), one column each, as bare names. No `key=value`, no trailing tab.
- An unpainted row with tags has its first tag in column 10. A painted row has `Painted` in column 10 and tags from column 11.
- The flags read are those of one pixel: `last_cont->metaDataFlags = Map_State->metaDataFlags + pixelIdx - 1;` (the fragment's last pixel, in `UpdateContigsFromMapState`).
- There are 64 tag slots (`u32 tags[64][16];` in `src/genomeData.h` L87). Names are user-editable, and "Load AGP" adds unknown tag names to free slots (`parse_tags` in `src/parse_agp.h`), so arbitrary strings can appear.
- Three tags are never exported: `vertPaint`, `horzPaint`, `crossPaint` (`src/grey_out_settings.h` L14, `paint_tags`).

The Sanger downstream parser takes everything after column 9 as tags: `tags=tuple(fields[9:])` with the comment "Tenth fields onwards added as tags metadata" (https://github.com/sanger-tol/agp-tpf-utils/blob/74af3fbc3a3a30a0c3434b3282f1dc44319493f5/src/tola/assembly/parser.py#L59-L60).

## 5. Cut contigs and inverted contigs

### Internal representation of a cut

`BreakMap` (L8852; the edit at L8920):

```cpp
// cut the contig by amending the original Contig Ids.
for (u32 tmp = loc + 1; tmp <= ptr_right; tmp++) // cut_loc is included as left
{   
    ...
    Map_State->originalContigIds[tmp] += Number_of_Original_Contigs;
}
```

and the inverse lookup (L1100):

```cpp
GetOriginalContigBaseId(u32 originalContigId)
{
    return Number_of_Original_Contigs ? (originalContigId % Number_of_Original_Contigs) : originalContigId;
}
```

So a fragment is identified internally by `originalContigId + k * Number_of_Original_Contigs` on its pixels. There is no fragment name. `UpdateContigsFromMapState` starts a new fragment whenever the raw id changes or the per-pixel relative coordinate stops running consecutively (L2300):

```cpp
if (original_contig_id != lastId_original_contig ||
    (inverted && coord != (lastCoord - 1)) ||
    (!inverted && coord != (lastCoord + 1)))
{
    // New contig or fragment of a contig
```

Fragments also arise without `BreakMap`: moving or inverting part of a contig in edit mode breaks the run of relative coordinates, which is the older (pre-1.0.3) way a contig got split.

### In the AGP

- A cut contig is several W rows with the same component id and tiling `component_beg..component_end` ranges, each at pixel resolution. No suffix, no fragment number.
- An inverted fragment has `-` in column 9, with component_beg/end still the low and high coordinate on the original contig. The `-` is suppressed to `+` for unpainted fragments and single-fragment painted scaffolds unless Format Singletons is on (section 2).

### What `GenerateAGP` does about cuts before writing

L13157-L13160:

```cpp
u32* tmp_orignal_contig_ids = new u32[Number_of_Pixels_1D];
for (u32 i = 0 ; i< Number_of_Pixels_1D; i++ )tmp_orignal_contig_ids[i] = Map_State->originalContigIds[i];
Map_State->restore_cutted_contigs_all(Number_of_Pixels_1D);
UpdateContigsFromMapState();
```

The intent is to undo `BreakMap` id offsets so that two pieces of a cut contig that are still adjacent and in the same orientation merge back into one row. In 1.0.6 and 1.0.7 that restore call does nothing (`src/genomeData.h` L104-L112 at 1.0.7):

```cpp
void restore_cutted_contigs_all(const u32& num_pixel_1d)
{
    for (u32 i = 0; i < num_pixel_1d; i++)
    {
        // These are now no-ops.  I don't understand what they originally did:
        // originalContigIds[i] = originalContigIds[i] % Max_Number_of_Contigs;
        originalContigIds[i] = originalContigIds[i];
    }
}
```

Consequence, read from the code (I did not run the binary): in 1.0.6 and 1.0.7 a Pixel Cut that was made but whose pieces were left in place still yields two W rows. If both pieces are in the same painted scaffold there is a 100 bp `U` gap row between them; if unpainted they are two separate `Scaffold_n` objects. In 1.0.3 to 1.0.5 and on `dev`, such adjacent pieces are merged into one row. See section 7.

## 6. Object order and naming

Scaffold ids are not the user's paint ids. They are renumbered 1, 2, 3, ... by position on the map each time `UpdateContigsFromMapState` runs (L2343-L2348):

```cpp
last_cont->scaffId =
    thisScaffID
        ? ((thisScaffID == lastScaffID) ? (scaffId) : (++scaffId))
        : 0;

// Save the scaffold ID
lastScaffID = thisScaffID;
```

A painted scaffold is therefore a contiguous run of pixels with the same paint id. If an unpainted fragment sits between two fragments painted with the same id, `lastScaffID` becomes 0 in between and the two sides get different numbers.

Output loop (L13182-L13192):

```cpp
u32 scaffId = 0;
u64 scaffCoord_Start = 1;
u32 scaffPart = 0;

u32 scaffId_unPainted = 0;
if (preserveOrder) ForLoop(Contigs->numberOfContigs) scaffId_unPainted = my_Max(scaffId_unPainted, (Contigs->contigs_arr + index)->scaffId);

for (   u08 type = 0; 
        type < (preserveOrder ? 1 : 2);  // two round: 1st round for painted scaffs, 2nd round for unpainted
        ++type) 
```

Default (Preserve Order off):

1. Pass 1 writes all painted scaffolds in map order as `Scaffold_1 .. Scaffold_K`, each a multi-row object (W, U, W, ...).
2. Pass 2 writes every unpainted fragment in map order, each as its own one-row object, numbered `Scaffold_K+1, K+2, ...` (`++scaffId` continues from the last painted id).

Preserve Order on: a single pass in map order. Painted scaffolds keep numbers 1..K; unpainted fragments are numbered from K+1 upward but appear interleaved where they sit on the map, so object names are not monotonic in the file.

All object names are `Scaffold_<n>`. The README says the same in prose (README.md L119 at 1.0.7): "Objects are first created according to the scaffolds defined in scaffolding mode, with remaining sequences output as singletons."

## 8. The pixel-resolution caveat and AGPCorrect

README.md at 1.0.7, L118-L125:

> # AGP Output
> Map state can be output in [AGP](https://www.ncbi.nlm.nih.gov/assembly/agp/AGP_Specification/) format via the UI. Objects are first created according to the scaffolds defined in scaffolding mode, with remaining sequences output as singletons.
> ## AGP Correction
> Note that object/part sizes will only be accurate up to the size of an individual map texel, and that any input sequences smaller than an individual texel will not be output.
> AGP files can be corrected by the included python script [AGPCorrect](https://github.com/wtsi-hpag/PretextView/blob/master/AGPCorrect), which requires access to the input sequences in (gzipped) FASTA format.
> ```bash
> AGPCorrect /path/to/ref.fa(.gz) /path/to/current/map.agp >/path/to/corrected_scaffs.agp
> ```

https://github.com/sanger-tol/PretextView/blob/1.0.7/README.md

What `AGPCorrect` does (https://github.com/sanger-tol/PretextView/blob/1.0.7/AGPCorrect, 93 lines, Python with Biopython):

```python
seen = {}
...
            if line[4] == "W":
                seen[line[5]] = max(seen.setdefault(line[5], 0), int(line[7]))
...
            line[1] = str(int(line[1]) + correct)

            if line[4] == "W" and ((this_l := int(line[7])) == seen[line[5]]):
                correct += (acc_l := seqs[line[5]]) - this_l
                ...
                line[7] = str(acc_l)

            line[2] = str(int(line[2]) + correct)
```

- For each contig it finds the largest component_end in the file. On the row that has that end, it replaces component_end with the true FASTA length and shifts later object coordinates in the same object by the difference.
- Only the last fragment of each contig is stretched. Internal cut positions stay at pixel boundaries.
- It appends every FASTA sequence missing from the AGP (the sub-pixel contigs) as new 9-column rows named `Scaffold_{maxn + k}`, `+` orientation, full length:

```python
"\t".join((f"Scaffold_{maxn + k}", "1", str(n), "1", "W", s, "1", str(n), "+"))
```

- It appends `\tModified by PretextView_AGPCorrect` to the `# DESCRIPTION` line.
- It rewrites columns 2, 3 and 8 only; extra columns (`Painted`, tags) pass through unchanged because it re-joins the whole split line.
- It assumes column 1 ends in `_<integer>` (`int(line[0].split("_")[-1])`) and that data lines have at least 8 tab fields.

The `# HiC MAP RESOLUTION: ... bp/texel` header line (section 1) is the in-file marker of this caveat. Nothing else in the file states that coordinates are approximate.
