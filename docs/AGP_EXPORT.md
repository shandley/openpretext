# AGP export and import

OpenPretext writes a curation as AGP in the layout PretextView uses, because
that file is what the tools after the map viewer read. This page describes the
file, how it was checked against those tools, and what it cannot tell you.

The code is in `src/export/AGPModel.ts`, `src/export/AGPWriter.ts` and
`src/formats/AGPParser.ts`. The sources this follows (PretextView's writer, the
downstream tools, the AGP specification) are quoted in
`research/export-compat-2026-11/`.

## Which file to export

The Export menu has two AGP entries.

**Export AGP (for curation pipelines)** writes the file PretextView would
write. Give it, with the FASTA the map was built from, to:

- `pretext-to-asm` from Sanger Tree of Life
  ([sanger-tol/agp-tpf-utils](https://github.com/sanger-tol/agp-tpf-utils)), or
- the VGP post-curation scripts
  ([vgl-hub/vgl-curation](https://github.com/vgl-hub/vgl-curation), also the
  Galaxy post-curation workflow).

Those tools build the curated FASTA themselves. They correct the coordinates
against the real sequence, name the chromosomes, and separate haplotigs and
contaminants. Do not give them OpenPretext's FASTA export.

**Export AGP (standard, 9 columns)** writes the same layout without the tag
columns, for validators and archives. NCBI's validator rejects a tenth column.

## The pipeline file

```
##agp-version	2.1
# DESCRIPTION: Generated by OpenPretext Version 0.1.0
# HiC MAP RESOLUTION: 1000.000000 bp/texel
Scaffold_1	1	200000	1	W	a1	1	200000	+	Painted	Z	Hap_1
Scaffold_1	200001	200100	2	U	100	scaffold	yes	proximity_ligation
Scaffold_1	200101	320100	3	W	a2	1	120000	+	Painted
Scaffold_1	320101	320200	4	U	100	scaffold	yes	proximity_ligation
Scaffold_1	320201	500200	5	W	a2	120001	300000	-	Painted	Unloc
Scaffold_2	1	124000	1	W	a3	1	124000	+
Scaffold_3	1	250000	1	W	a4	1	250000	+	Contaminant
Scaffold_4	1	150000	1	W	a5	1	150000	+
```

This is the file the browser test `tests/e2e/agp-export-import.spec.ts`
checks: a small map of five sequences where `a2` was cut 120 texels in, its
right piece inverted, and `a1` and both pieces painted into one scaffold.


**Header.** The third line gives the map's resolution in base pairs per texel
(one texel is one pixel of the full-resolution map). `pretext-to-asm` will not
run without it and reads its tolerance from it.

**Sequence rows.** Column 6 is always the name of a sequence in the input
assembly, and columns 7 and 8 are an interval of that sequence. A contig that
was cut appears as several rows with the same name and intervals that meet
exactly. OpenPretext's own names for cut pieces (`name_L`, `name_R`) never
appear in the file.

**Coordinates.** They are computed from texels alone, as PretextView computes
them: a piece that starts `p` texels into its sequence and is `n` texels wide
runs from `floor(p × L / N) + 1` to `floor((p + n) × L / N)`, where `L` is the
genome length in the map header and `N` is the map's width in texels. So every
cut coordinate is a multiple of the resolution, and the last coordinate of a
sequence is its last texel boundary, which is near its true length but not
equal to it. The downstream tools expect this and correct it: `pretext-to-asm`
moves a breakpoint that falls within about one texel of a gap onto the gap and
takes the true ends from the FASTA.

**Gap rows.** `U 100 scaffold yes proximity_ligation` between every pair of
neighbouring rows in an object. The 100 is what the AGP specification requires
for a gap of unknown size. It is not a measurement.

**Objects.** A scaffold you painted is one object. Objects are named
`Scaffold_1`, `Scaffold_2`, and so on: painted scaffolds first, in the order
they sit on the map, then every contig that is not in a scaffold as an object
of its own. If the same scaffold is painted in two places with other contigs
between, it is written as two objects, because an object is a run of
neighbours. The names you give scaffolds in the sidebar are not written; the
downstream tools name chromosomes themselves (`SUPER_1` and so on, by size).

**Orientation.** `-` means the piece is reverse-complemented, and is written
wherever the map shows it so, including on an object of a single row. That
matters for a chromosome made of one scaffold that you turned round:
`pretext-to-asm` reverse-complements it on seeing `-`. PretextView up to 1.0.7
writes `+` on single-row objects unless its "Format Singletons" option is
ticked; its next release always follows the map, as OpenPretext does.

**Columns 10 onward.** `Painted` on every row of a painted scaffold, then the
contig's tags, one per column.

### Tags

Tags are matched exactly, with case, by the tools that read them. OpenPretext
offers the vocabulary those tools know:

| Tag | What the Sanger tool does with it |
|---|---|
| `Haplotig` | Moves the row to a separate haplotigs file |
| `Contaminant` | Moves the row to a separate contaminants file |
| `FalseDuplicate` | Moves the row to a separate file |
| `Unloc` | Makes the row an unlocalised scaffold of its chromosome. The contig must be painted into that chromosome's scaffold |
| `X`, `Y`, `Z`, `W`, `X1`, `B1`, ... | Names the chromosome (`SUPER_X`). One name per scaffold; put it on any one row |
| `Hap1`, `HAP1`, `Hap_1`, ... | Names the haplotype. Any word the tool does not know is read as a haplotype name |
| `Target`, `Primary`, `Singleton` | Switches described in the tool's own help |

The VGP scripts need `Hap_1` and `Hap_2` (with the underscore) and read only
`Unloc`, `Haplotig`, `X`, `Y`, `Z` and `W`, in the column straight after
`Painted`. OpenPretext writes those tags before haplotype tags, so they land
there.

Because an unknown word is silently taken for a haplotype, the sidebar refuses
anything that is not one word and questions near misses such as `haplotig`.

### Excluded contigs

An excluded contig is written, with its tags. It has to be: if a row is
missing, `pretext-to-asm` puts the sequence back as an unplaced scaffold, and
if a piece of a cut sequence is missing it stops with an error. The tool
removes sequence by tag.

So every excluded contig must carry `Haplotig`, `Contaminant` or
`FalseDuplicate`. If one does not, the export stops and names it.

### What stops the export

- An excluded contig with no tag saying why it is removed.
- `Unloc` on a contig that is not in a scaffold.
- More than one chromosome name, or more than one haplotype tag, in one scaffold.

Each of these is an error in `pretext-to-asm` or a silent mistake downstream.

### Sequences too small for the map

A sequence shorter than about one texel owns no texel and has no row, as in
PretextView's file. `pretext-to-asm` adds back every input sequence the AGP
does not mention, as an unplaced scaffold, so nothing is lost.

## The standard file

The same objects and rows, with these differences:

- Nine columns: no `Painted`, no tags.
- The version line is `##agp-version 2.1` with a space, as the specification
  writes it.
- Excluded contigs are left out, and the object closes up around them.
- An object of a single row is written `+`, as the specification asks of a
  singleton.

Coordinates are still texel-resolution, and component names are still the
input sequences'. To submit an assembly, use the files the downstream tool
produces from the pipeline AGP, not this one.

## How this was checked

- **Against a released curation.** `test-data/case-study/quail` holds the king
  quail map and the AGP PretextView 0.2.5 wrote from the Sanger curation of it.
  Importing that AGP onto the map and exporting again reproduces all 605 rows
  exactly (`tests/unit/agp-quail-roundtrip.test.ts`).
- **Against the Sanger tool.** `bench/agp-acceptance.ts` takes the 14 real
  curations in `agp-tpf-utils`' own test data, reads each PretextView AGP into
  OpenPretext, writes it back, runs `pretext-to-asm` on OpenPretext's file,
  and compares every output with the result that repository expects. All 14
  give identical output.
- **Against the specification.** `tests/helpers/agpValidate.ts` checks the
  rules a writer can break (contiguous coordinates, part numbers, span
  equality, gap rows, allowed values). Both files pass it over 80 random
  curations (`tests/unit/agp-export.test.ts`).

The first two need files that are not committed (they are large, or belong to
another repository) and are skipped where absent; the third runs everywhere.

Not checked: NCBI's `agp_validate` has not been run on the standard file, the
VGP scripts have not been run on the pipeline file, and nothing has been
submitted to ENA, whose validator source does not list `proximity_ligation`
among the gap evidence it accepts.

## Importing an AGP

**Import AGP** (in the command palette, Cmd+K) applies an AGP to the loaded map: its cuts, order,
orientation, scaffolds and tags. It reads PretextView's file, OpenPretext's,
and plain nine-column AGP. It replaces the current curation and clears the
undo history, like opening a session. The file is checked against the map
first, and nothing changes if it does not fit.

- A sequence named on one row is taken whole. One named on several rows is cut
  at their coordinates, which are moved to the nearest texel boundary if they
  are not on one (a corrected AGP reads this way), with a warning.
- An AGP whose sequences are not in the map, or whose resolution header gives
  a different resolution, is refused. So is one whose rows overlap.
- Whatever the AGP does not place is kept and put at the end.
- In PretextView's layout, `Painted` decides which objects are scaffolds. In
  plain AGP, an object of several rows is a scaffold.

An AGP does not record everything:

- **Exclusions.** Tags come back; whether a contig was excluded does not.
- **Where unpainted contigs sat.** The file lists painted scaffolds first, so
  an unpainted contig that sat between two scaffolds comes back after them.
- **Scaffold names, undo history, waypoints.** Use a session file to keep a
  curation exactly as it was.

## FASTA and BED

**Export FASTA** writes one record per curated contig, in curated order,
reverse-complemented where inverted, with excluded contigs left out. Each
record is cut from the input sequences at the same coordinates as the AGP
rows, so the two files agree. The piece that reaches the end of a sequence runs
to the sequence's true end, so no base is lost or repeated. A sequence too
small to own a texel is written whole, as a record of its own. Records are
contigs, not scaffolds: no gaps are inserted.

Cuts in this FASTA are at texel boundaries, not at assembly gaps. It is a
faithful copy of what the map shows, useful for inspection. For an assembly to
submit, run the downstream tool on the pipeline AGP.

**Export BED** is the standard AGP's layout as BED6, one line per sequence
row, named `sequence:begin-end`. No curation pipeline reads it.
